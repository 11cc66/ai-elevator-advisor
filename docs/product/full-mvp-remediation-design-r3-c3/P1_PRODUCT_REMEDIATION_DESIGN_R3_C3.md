# P1 Product Remediation Design R3-C3

Status:

```text
R3-C3 DESIGN COMPLETE WITH OPEN BLOCKERS
```

R3-C3 is design-only. No source, Schema, Migration, database, Storage, Build,
Native RPC, Runtime or deployment operation is authorized.

## 1. Scope and Baseline

This document supersedes R3-C2 only for the corrected design areas. It retains
all R1/R2/R3 designs that passed prior independent review.

Current implementation is still the DEMO/Mock implementation:

- `apps/web/src/modules/selection/service.ts:17-54` reads
  `requirement.fields`;
- `apps/web/src/modules/advisor/service.ts:25-153` writes JSON requirement
  versions;
- `prisma/schema.prisma:868-1098` contains the current CUID/String schema and
  no R3-C3 tables.

The C3 model is proposed future design.

## 2. Canonical Identity

### 2.1 Selected strategy

C3 chooses **Option A: retain the existing CUID/Text identity system**.

```text
CanonicalEntityId = TEXT
format = 1..64 ASCII characters, generated by CUID
sourceKey = TEXT
```

No native UUID is introduced for existing business IDs. This avoids an
unreviewed repository-wide primary-key conversion and preserves existing CUID
foreign keys.

`sourceKey` is a namespaced canonical text identity:

```text
assertion:<assertionId>
professional-event:<eventId>
catalog-evidence:<evidenceObjectId>
session-system:<systemRuleRevisionId>:<assertionId>
```

The prefix is part of the source identity. The database uses exact text
equality; it does not cast CUID to UUID or vice versa.

### 2.2 Identity invariants

- Every entity ID remains `TEXT`, bounded to 64 ASCII characters.
- New IDs are server-generated CUIDs.
- Existing CUIDs are not rewritten.
- A sourceKey is immutable and uniquely identifies one source kind/ID tuple.
- Composite FKs use text columns consistently.
- No `CAST(id AS uuid)` is permitted in a security or ownership decision.
- `rowId` in R3-BASIS-1 is the canonical text row identity, length-prefixed
  UTF-8; it is not a native UUID.
- A missing/empty/overlong ID or sourceKey is rejected.

### 2.3 Migration

1. Freeze writes to affected R3-C3 tables during the expand window.
2. Add text columns and sourceKey columns with nullable temporary state.
3. Backfill existing CUID references and source keys deterministically.
4. Detect unrepresentable legacy sources and quarantine them.
5. Validate length/format, sourceKey uniqueness and composite FKs.
6. Set NOT NULL and resume writes.
7. Never rewrite an existing CUID or external URL as part of backfill.

Detailed mapping and rollback limits are in
`R3_C3_IDENTITY_AND_MIGRATION_DESIGN.md`.

## 3. Requirement Model

### 3.1 Ownership chain

```text
Project
  -> AdvisorConversation
      -> Requirement
          -> RequirementVersion
              -> RequirementFieldValue
                  -> RequirementFieldAssertion
                      -> AdvisorMessage
```

All ownership columns are `TEXT NOT NULL` for new rows. The final
`RequirementVersion` keys are:

```text
UNIQUE(requirementId, versionNumber)
UNIQUE(id, requirementId, projectId, conversationId)
UNIQUE(id, requirementId, projectId, conversationId, installationScenario)
```

They are the exact parent keys used by all descendants.

## 4. ProfessionalReview Source Binding

### 4.1 Event parent key

`ProfessionalReviewEvent` carries the full review owner identity:

```text
ProfessionalReviewEvent
  id TEXT PRIMARY KEY
  reviewId TEXT NOT NULL
  projectId TEXT NOT NULL
  conversationId TEXT NOT NULL
  requirementId TEXT NOT NULL
  requirementVersionId TEXT NOT NULL
  installationScenario NOT NULL
  eventSequence INTEGER NOT NULL
  resultingStateVersion INTEGER NOT NULL
  previousState TEXT NULL
  newState TEXT NOT NULL
  actorUserId TEXT NOT NULL
  actorAuthorityId TEXT NOT NULL
  decision TEXT NULL
  reason TEXT NULL
  occurredAt TIMESTAMPTZ(6) NOT NULL
  basisDigest TEXT NOT NULL
  policyRevisionId TEXT NOT NULL
  requestId TEXT NOT NULL
  UNIQUE(reviewId, eventSequence)
  UNIQUE(reviewId, resultingStateVersion)
  UNIQUE(reviewId, requestId)
  UNIQUE(id, reviewId, projectId, conversationId, requirementId,
         requirementVersionId, installationScenario)
  FK(reviewId, projectId, conversationId, requirementId,
     requirementVersionId, installationScenario)
    -> ProfessionalReview(id, projectId, conversationId, requirementId,
                          requirementVersionId, installationScenario)
  FK(actorUserId) -> User(id)
```

The `ProfessionalReview` header has the same six-column owner key, plus its
candidate, policy and basis. The event key is the exact FK target used by
Assertion/FieldValue.

### 4.2 Transition protocol

The event table remains the only state authority. There is no mutable
`ProfessionalReview.state` or `stateVersion` truth.

`transition_professional_review`:

1. acquires a row lock on the review header;
2. reads the latest event by `(reviewId,eventSequence DESC)`;
3. verifies caller, policy, exact basis, candidate and event predecessor;
4. checks expected state/version;
5. inserts exactly one event;
6. commits.

The function is a fixed `SECURITY DEFINER` function owned by the approved
database transition owner, with a fixed `pg_catalog`/approved-schema
`search_path`, and EXECUTE is revoked from PUBLIC. Ordinary application roles
have no direct INSERT/UPDATE/DELETE on the event table. The exact owner/grants
are `OD-R3-C2-03` and must be verified before implementation.

## 5. RuleSet Event-Only State

RuleSet follows the same event-only pattern:

- `SelectionRuleSetRevision` is immutable content plus authority source,
  policy and content digest.
- `SelectionRuleSetReviewEvent` carries `ruleSetRevisionId`, event sequence,
  previous/new status, policy revision, actor, authority, basis digest,
  request id and timestamp.
- `selection_rule_set_current` is a read-only latest-event view.
- No `APPROVED` boolean/status is authoritative on the revision row.
- `SelectionRun` binds exact `ruleSetRevisionId`.

The transition function checks exact revision, policy, basis, previous status
and expected status version. Direct event DML and direct status writes are
denied. Function ownership/grant details are finalized under
`OD-R3-C2-03`.

## 6. R3-BASIS-1 Revision 3

The full normative protocol is in
`R3_BASIS_V3_PROTOCOL_AND_VECTOR_SPEC.md`. In summary:

```text
Magic:              R3BASIS\0 (8 bytes)
Version:            0x0003
Payload type:       0x0001
Header length:      28 bytes
Record length:      uint32be, includes itself
Record type:        uint16be
rowId:              uint16be length + UTF-8 ASCII CUID text
stableKey:          uint16be length + UTF-8 NFC bytes
field count:        uint16be
Field:              tag u16, type u8, presence u8, length u32, value
Sort:               recordType, stableKey bytes, rowId bytes;
                    fieldTag ascending
Reject:             duplicate record key, unknown type, invalid UTF-8,
                    overflow, unconsumed bytes
```

The row identity is canonical text/CUID, not native UUID. This aligns the
protocol with the repository's current IDs.

## 7. Snapshot Source and Authority

Snapshot fields use:

```text
sourceFieldValueId
sourceKind
sourceKey
```

with an exact FK to the FieldValue parent key including the RequirementVersion,
Requirement, Project, Conversation, scenario and source identity.

`USER_ASSERTION` requires:

```text
sourceKey = 'assertion:' || sourceAssertionId
```

`PROFESSIONAL_REVIEW` requires:

```text
sourceKey = 'professional-event:' || sourceProfessionalReviewEventId
```

and a composite event FK proves that the event belongs to the same
Project/Conversation/Requirement/Version.

The normalized snapshot rows are the sole authority. The JCS payload is a
read-only reconstruction; no payload column/table is writable.

The snapshot header retains exact Case/Project/RequirementVersion/SelectionRun
and RuleSetRevision keys. The creation function inserts all run candidates
exactly once, copies immutable values, computes R3-BASIS-1 revision 3 bytes
and checks them at deferred COMMIT. Source withdrawal and later catalog changes
only produce a read-time basis diff.

## 8. Typed Field Catalogue

The physical column types are:

```text
BOOLEAN       BOOLEAN
INTEGER       BIGINT
DECIMAL       NUMERIC(18,6)
TEXT          TEXT with maximum 4,000 Unicode code points
ENUM          VARCHAR(64) allowlisted
CANONICAL_ID  VARCHAR(64) ASCII [A-Za-z0-9:_-]
TIMESTAMP     TIMESTAMPTZ(6)
BYTES         BYTEA with maximum 1 MiB
NULL          no typed value
```

Units are explicit non-empty text from an approved field/unit catalogue.
No hard engineering threshold or unit conversion is approved by C3. Those
remain business/technical decisions. Unknown units, type/value mismatch,
out-of-range values and non-normalized decimal text are rejected.

## 9. Legacy Quarantine

```text
RequirementLegacyQuarantine
  id TEXT PRIMARY KEY
  legacyRequirementId TEXT NOT NULL
  projectId TEXT NOT NULL
  sourceKind TEXT NOT NULL
  reasonCode TEXT NOT NULL
  evidenceJson JSONB NOT NULL
  status OPEN | RESOLVED
  resolvedByUserId TEXT NULL
  createdAt TIMESTAMPTZ(6) NOT NULL
  UNIQUE(legacyRequirementId, reasonCode)
```

Unknown, inaccessible, corrupted or unsupported historical sources are
quarantined rather than mapped to `SYSTEM_DERIVED`. A quarantine can be
resolved only by a separately approved data/security workflow, preserving the
original evidence and audit.

## 10. Transactions and Failure Recovery

- Requirement writes: conversation/version lock, typed value/assertion,
  confirmation, source message, JSON projection and pointer in one transaction.
- RuleSet/ProfessionalReview transitions: row lock, latest-event read,
  policy/basis check, one event insert, commit.
- Snapshot creation: case lock, exact basis read, all normalized rows,
  R3-BASIS-1 digest, deferred checks, pointer and audit in one transaction.
- Catalog capture: archive write before evidence metadata; orphan archive
  objects remain non-authoritative.
- Idempotency: success has one committed request/business row; deterministic
  replayable failure has a separate failure record; unexpected errors roll
  back; commit-unknown uses a new-connection key read.

No failed/unknown relation becomes `OPERATIONAL`, `APPROVED`, or a trusted
Snapshot.

## 11. P1-3 Boundary

C3 does not modify Upload Intent, Upload Attempt, Lifecycle, FileVersion,
Operation Attempts, P1-3 migration or triggers. Catalog evidence archive is a
separate capability. No Storage path is used by this design.
