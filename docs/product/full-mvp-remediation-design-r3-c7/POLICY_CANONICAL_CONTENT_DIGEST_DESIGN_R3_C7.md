# Policy Canonical Content and Digest Design R3-C7

Artifact: `POLICY_CANONICAL_CONTENT_DIGEST_DESIGN_R3_C7.md`

Metadata authority: `SHA256SUMS_R3_C7.txt`.

## 1. Authority

The policy content authority is canonical JSON text generated by PostgreSQL 18:

```text
canonical_text = input_text::jsonb::text
```

The design accepts text, not a caller-provided digest:

```text
create_policy_revision(
  policy_id, policy_kind, scope_project_id, revision_number,
  content_text, supersedes_revision_id, request_id, request_key, reason
)
```

Inside the trusted function:

```text
canonical_bytes = UTF8(canonical_text)
digest = SHA-256("AIEA-POLICY\0v1\0" || canonical_bytes)
```

Algorithm and content version are domain-separated and stored as
`content_version=1`.

## 2. Canonicalization Rules

PostgreSQL `jsonb` provides:

- insignificant whitespace removal;
- canonical object key ordering;
- JSON number normalization;
- duplicate-key collapse at parse time;
- exact Unicode code points after JSON escape decoding.

To prevent silent duplicate-key collapse, `policy_digest` requires:

```text
input_text::jsonb::text = input_text
```

Therefore a noncanonical representation or duplicate key does not hash the
same canonical text and rejects before insert.

Unicode is **not** normalized. The exact decoded code points are authoritative.
This avoids a hidden cross-language normalization step. Producers that need
semantic Unicode equivalence must establish it as policy content, not rely on
the database.

## 3. No Caller Digest

The previous `p_content_digest` parameter is removed. A caller cannot approve
arbitrary bytes while claiming a different digest.

`app.policy_digest(text)` is immutable and computes the digest. The Revision
guard independently recomputes it from stored canonical bytes.

## 4. Byte-Change Counterexample

| Attempt | Result |
|---|---|
| Modify one canonical content byte, keep old digest | Revision trigger digest mismatch |
| Submit caller digest different from content | No digest argument exists |
| Submit noncanonical JSON whitespace | `input::jsonb::text <> input` rejects |
| Submit duplicate key | JSONB canonical text differs from input and rejects |
| Reuse old approval event after content change | Revision is immutable; digest/event mismatch |
| Change Revision digest through UPDATE | Revision UPDATE trigger rejects |
| Delete and recreate same revision | ID/revision/event history constraints prevent silent replacement |

## 5. Versioning

Any change to canonicalization or digest format requires:

- new `content_version`;
- distinct digest domain;
- compatibility/read-only treatment of old revisions;
- separate Open Decision approval;
- independent cross-language vectors.

No implicit upgrade is permitted.
